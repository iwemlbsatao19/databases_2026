# ДЗ №2. Вариант 2: Служба доставки еды (Food Delivery)

Скрипты: `sql/01_hw2_tables.sql` (Часть 1) и `sql/02_hw2_violations.sql` (Часть 2).
Оба работают поверх схемы `food_delivery`, созданной в ДЗ №1. Тестовые данные
из `02_seed.sql` нужны обязательно: демонстрации применяют промокод к настоящему заказу.

## Часть 1. Дополнение схемы

Добавлены две таблицы: `promo_codes` и `order_promotions`. Тема выбрана не случайно —
скидок в модели ДЗ №1 не было, а без них сервис доставки не работает.

### `promo_codes` — промокоды и акции

Первичный ключ `promo_code_id` типа `bigint`, суррогатный.

Код акции `code` типа `varchar(32)` — это `NOT NULL UNIQUE`, то есть бизнес-ключ.
Дополнительно на него стоит `CHECK` на формат `^[A-Z0-9_-]{4,32}$`, чтобы в базу
не попадали коды с пробелами и кириллицей. Описание `description` типа `varchar(200)`
объявлено `NOT NULL`: акция без описания просто не покажется в интерфейсе.

Тип скидки `discount_kind` — перечислимый тип со значениями `percent`, `fixed`
и `free_delivery`. Размер скидки `discount_value` типа `numeric(10,2)` с ограничением
`CHECK (discount_value > 0)`. Минимальная сумма заказа `min_order_amount` того же типа
с проверкой на неотрицательность — ниже этой суммы промокод не срабатывает.

Ссылка на ресторан `restaurant_id` — внешний ключ на `restaurants`, и он намеренно
**допускает `NULL`**: пустое значение означает, что акция действует во всех ресторанах
сервиса сразу, а заполненное — что только в одном.

Период действия задаётся парой `valid_from` и `valid_to` типа `timestamptz`
с ограничением `CHECK (valid_to > valid_from)`: период не может закончиться раньше,
чем начался. Лимит использований `usage_limit` и счётчик `used_count` связаны
ограничением `CHECK (usage_limit IS NULL OR used_count <= usage_limit)` — превысить
лимит невозможно, а `NULL` в лимите означает «без ограничений».

Флаг `is_active` нужен, чтобы выводить промокод из обращения, не удаляя его.

Отдельно стоит сложный `CHECK`, зависящий от соседней колонки:

```sql
CHECK (discount_kind <> 'percent' OR discount_value <= 100)
```

Для фиксированной скидки значение 150 — это 150 рублей, нормально. Для процентной
150 — это 150%, то есть сервис доплачивает клиенту. Одним ограничением
на `discount_value` такое правило не выразить, нужна проверка по паре колонок.

### `order_promotions` — применение промокодов к заказам

Первичный ключ составной: `(order_id, promo_code_id)`. Обе его части одновременно
являются внешними ключами — `order_id` ссылается на `orders` с правилом
`ON DELETE CASCADE`, а `promo_code_id` на `promo_codes` с правилом `ON DELETE RESTRICT`.

Размер скидки в рублях `discount_amount` типа `numeric(10,2)` объявлен `NOT NULL`
с ограничением `CHECK (discount_amount > 0)`. Время применения `applied_at`
типа `timestamptz` со значением по умолчанию `now()`.

`discount_amount` хранится, а не пересчитывается по `promo_codes`. Условия акции
могли измениться после оформления заказа, а чек должен остаться тем, который клиент
видел при оплате. Это то же решение, что и `order_items.unit_price` в ДЗ №1.

### Реализация связи M:N

Связь «заказ ↔ промокод» логически многие-ко-многим: один промокод применяют тысячи
пользователей к своим заказам, и одновременно к одному заказу можно применить
несколько промокодов сразу — например, «бесплатная доставка» вместе с «300 рублей
на первый заказ».

Реляционная модель не выражает M:N напрямую. Способ реализации — ассоциативная
таблица с составным первичным ключом `(order_id, promo_code_id)`.

Составной ключ выбран вместо суррогатного `id` по трём причинам. Во-первых, он сам
по себе является бизнес-правилом: один промокод применяется к одному заказу не более
одного раза, повторная вставка отбивается первичным ключом, и отдельное ограничение
не нужно. Во-вторых, он делает связь `orders` — `order_promotions` идентифицирующей:
применение скидки не существует вне своего заказа. В-третьих, первый столбец ключа
обслуживает самый частый запрос к таблице — «какие скидки в этом заказе», поэтому
отдельный индекс по `order_id` не нужен.

Плата за это решение: если однажды понадобится применять один промокод к заказу
дважды — скажем, при частичном возврате — схему придётся менять. По текущим
бизнес-правилам такого сценария нет.

### Что произойдёт при `DROP ... CASCADE`

Это проверено на практике, а не взято из документации. Результат неочевидный и важный.

```sql
DROP TABLE promo_codes CASCADE;
```

PostgreSQL сообщает:

```
NOTICE:  drop cascades to constraint fk_order_promotions_promo on table order_promotions
```

То есть `CASCADE` удаляет не связанные строки, а зависимые объекты схемы. Таблица
`order_promotions` остаётся на месте вместе со всеми своими строками, но внешний ключ
с неё исчезает. До удаления в таблице была одна строка и два внешних ключа, после
удаления — та же одна строка, но внешний ключ остался только один, на `orders`.
Значение `promo_code_id = 1` продолжает храниться в строке, хотя акции с таким
номером больше не существует, и база об этом молчит: проверять стало нечем.

Отсюда два вывода. Первый: `DROP TABLE ... CASCADE` не чистит данные, он снимает
ограничения, которые мешают удалить таблицу. Целостность после такой операции
нарушена молча, и обнаружится это позже — при попытке соединить таблицы. Второй:
`ON DELETE CASCADE` и `DROP ... CASCADE` — разные вещи. Первое про строки: удаление
заказа удаляет его скидки. Второе про объекты схемы: удаление таблицы удаляет
ограничения, а строки остаются сиротами.

Безопасный способ убрать таблицу — сначала удалить зависимые данные, потом саму
таблицу, либо снести всю схему целиком: `DROP SCHEMA food_delivery CASCADE` удаляет
объекты вместе с содержимым, и сирот не остаётся. Именно так устроена
перезапускаемость скриптов ДЗ №1.

Для `order_promotions` выбраны разные политики с двух сторон именно из-за этого.
`ON DELETE CASCADE` на `orders` — удалили заказ, его скидки бессмысленны.
`ON DELETE RESTRICT` на `promo_codes` — промокод, по которому прошли заказы, удалить
нельзя, иначе суммы в старых чеках перестанут сходиться. Это ограничение
демонстрируется в пятом блоке скрипта.

### Изменения в таблице `orders`

Скидка, которая не влияет на сумму заказа, — фикция, поэтому существующая таблица
приведена в соответствие:

```sql
ALTER TABLE orders ADD COLUMN discount_total numeric(10,2) NOT NULL DEFAULT 0;

ALTER TABLE orders ADD CONSTRAINT chk_orders_discount_not_over_total
    CHECK (discount_total <= items_total + delivery_fee);

ALTER TABLE orders ADD COLUMN total_amount numeric(12,2)
    GENERATED ALWAYS AS (items_total + delivery_fee - discount_total) STORED;
```

Второй `CHECK` не даёт скидке превысить стоимость заказа: отрицательный чек означал бы,
что сервис перечисляет деньги клиенту.

Тут есть подвох, который пришлось учесть. Колонка `total_amount` входит в покрывающий
индекс `idx_orders_restaurant_revenue` — тот самый, который обслуживает частый запрос
№4 «выручка ресторана за месяц». `DROP COLUMN` удаляет индекс вместе с колонкой, молча.
Если его не пересоздать, отчёт о выручке потеряет `Index Only Scan` и начнёт читать
таблицу целиком. Поэтому в конце скрипта индекс создаётся заново.

### Индексы

`idx_promo_codes_restaurant_id` и `idx_order_promotions_promo_code_id` построены
на внешних ключах: PostgreSQL не индексирует их автоматически. Второй заодно
обслуживает запрос «сколько раз использован промокод».

`idx_promo_codes_active_period` — частичный, с условием `WHERE is_active`.
Он обслуживает витрину «какие акции идут сейчас»: неактивные промокоды в неё
не попадают никогда, поэтому в индексе их нет вообще.

`idx_promo_codes_lookup` — частичный и одновременно покрывающий. Он обслуживает
проверку кода при оформлении заказа, а благодаря `INCLUDE` отдаёт тип и размер
скидки прямо из индекса, не обращаясь к таблице.

`idx_orders_restaurant_revenue` пересоздан после изменения колонки `total_amount`.

Отдельный индекс по `order_promotions.order_id` не создаётся: он уже первый столбец
составного первичного ключа.
