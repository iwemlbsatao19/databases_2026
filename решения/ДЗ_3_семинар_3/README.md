## Q1. Уникальные рейсы и сортировка

### 1. Чем `DISTINCT` отличается от `GROUP BY` и могут ли они разойтись

**По набору данных — не разойдутся никогда.** Оба запроса дают 710 строк, проверка через `EXCEPT` возвращает 0 расхождений. Обе конструкции группируют по тому же оператору равенства из btree-класса, и обе считают все `NULL` одной группой.

**По плану выполнения — в PostgreSQL 16 на этом запросе планы совпали вплоть до счётчика буферов.**

```
Sort  (actual rows=710)
  Sort Key: flight_no
  Sort Method: quicksort  Memory: 36kB
  ->  HashAggregate  (actual rows=710)
        Group Key: flight_no
        Batches: 1  Memory Usage: 73kB
        ->  Seq Scan on flights  (actual rows=65664)
              Buffers: shared hit=832
```

Для обоих вариантов — одинаково, время 22.2 мс против 22.6 мс (разница в пределах шума).

Но совпадение не гарантировано, это два разных узла планирования. Разойтись они могут, когда:

- по столбцу есть индекс — тогда возможен `Index Only Scan` + `Unique` вместо хеширования;
- не хватает `work_mem` — хеш-агрегация уступит место `GroupAggregate` с сортировкой, и у двух форм запроса оценки стоимости могут оказаться по разные стороны порога;
- в запросе появляются агрегаты или `HAVING` — тогда `DISTINCT` просто неприменим, это уже не эквивалентные конструкции.

Практический вывод: выбирать нужно по смыслу. `DISTINCT` — когда задача в устранении дублей, `GROUP BY` — когда по группам что-то считается.

### 2. Почему достаточно `ORDER BY` без `ASC` и что будет с разным регистром

`ASC` — значение по умолчанию по стандарту SQL, писать его не нужно. `NULL` при возрастании идут последними (`NULLS LAST`), это тоже умолчание PostgreSQL.

С регистром сложнее: порядок зависит не от SQL, а от **правила сравнения строк (collation) базы**. Эта база создана с `datcollate = C.UTF-8`, то есть сравнение побайтовое:

```
побайтово (C):          PG0001 < PG0002 < Pg0001 < pg0001 < pg0002
лингвистически (ICU):   pg0001 < Pg0001 < PG0001 < pg0002 < PG0002
```

Разница принципиальная. В локали `C` сравниваются коды символов, и `G` (0x47) меньше `g` (0x67) — поэтому **все** заглавные варианты уходят вперёд, и `PG0002` оказывается раньше `Pg0001`. В лингвистической локали регистр — признак третьего порядка: сначала сравниваются буквы, потом цифры, и только при полном совпадении — регистр. Поэтому `pg0001` и `PG0001` стоят рядом.

Отдельно стоит отметить: в самих данных все 65 664 номера записаны заглавными, так что на этой базе вопрос гипотетический. И ещё `flight_no` имеет тип `character(6)`, а не `varchar`, — при сравнении хвостовые пробелы игнорируются.

## Q2. Аэропорты и выручка за билеты

### 1. Два билета одного пассажира на один рейс и двойной счёт

**Да, `COUNT(*)` посчитал бы такого пассажира дважды.** В схеме ничто этого не запрещает: первичный ключ `ticket_flights` — это `(ticket_no, flight_id)`, а один человек может купить два разных билета на один рейс.

В данных этой базы таких случаев **ноль** — проверено группировкой по `(flight_id, passenger_id)` с `HAVING count(*) > 1`. Но полагаться на это нельзя, ограничения в схеме нет.

Поэтому в запросе стоит `count(DISTINCT t.passenger_id)`.

Важная тонкость: **на выручку это не распространяется**. Два билета — это две реально полученные суммы, и `SUM(amount)` обязан сложить обе. `DISTINCT` нужен только счётчику людей. Если применить `SUM(DISTINCT amount)`, два билета по одинаковой цене схлопнутся в один и выручка окажется занижена.

### 2. Рейсы без единого проданного билета

`INNER JOIN` выбрасывает их молча. Цифры для этой базы:

```
всего рейсов:            65 664
рейсов с билетами:       45 174
потерялось бы:           20 490
```

То есть **31% рейсов** просто исчез бы из отчёта — в основном это будущие рейсы со статусом `Scheduled`.

Нужен `LEFT JOIN` от `flights`: он сохраняет левую строку, даже когда справа совпадений нет, подставляя `NULL`. Но дальше есть две ловушки, обе проверены на рейсе 182 (он без билетов):

| Выражение | Результат | Верно? |
|---|---|---|
| `SUM(tf.amount)` | `NULL` | нет, нужен `COALESCE(..., 0)` |
| `COUNT(*)` | `1` | **нет** — считается сама строка рейса |
| `COUNT(tf.ticket_no)` | `0` | да |

`COUNT(*)` считает строки результата соединения, а после `LEFT JOIN` строка есть всегда — с `NULL` в правой части. `COUNT(столбец)` пропускает `NULL`, поэтому даёт честный ноль.

## Q3. Отменённые рейсы и города

### 1. Аэропорты, которых нет в таблице рейсов

`NOT EXISTS` обрабатывает их правильно сам по себе: если для аэропорта не нашлось ни одной строки в `flights`, подзапрос пуст, `NOT EXISTS` истинно, город попадает в результат. Это логично и по смыслу — «из города не было ни одного отменённого рейса» верно и тогда, когда рейсов не было вообще.

В этой базе проверка даёт 0: все 104 аэропорта хотя бы раз фигурируют как аэропорт вылета. Из 101 города условию удовлетворяет ровно один — **Bratsk**.

Отдельно стоит поправить формулировку из задания: `city NOT IN (SELECT departure_airport ...)` сравнивает название города с трёхбуквенным кодом аэропорта. Это сопоставление разных сущностей, оно не даст совпадений никогда. Сравнивать нужно `a.airport_code` с `f.departure_airport`, а `DISTINCT city` брать уже в выводе — в одном городе может быть несколько аэропортов.

### 2. Ловушка `NOT IN` с `NULL`

**В этой базе ловушка не срабатывает**, потому что `flights.status` и `flights.departure_airport` объявлены `NOT NULL` — подзапрос физически не может вернуть `NULL`. Поэтому я воспроизвёл её искусственно, добавив в подзапрос один `UNION ALL SELECT NULL`:

| Запрос | Результат |
|---|---|
| `NOT IN`, подзапрос без `NULL` | 1 строка |
| `NOT IN`, подзапрос с одним `NULL` | **0 строк** |
| `NOT EXISTS`, тот же подзапрос с `NULL` | 1 строка |

Механика в трёхзначной логике. `x NOT IN (a, b, NULL)` разворачивается в `x <> a AND x <> b AND x <> NULL`. Последнее сравнение даёт не `FALSE`, а `UNKNOWN`:

```
'AAA' <> NULL        →  NULL
'AAA' NOT IN (NULL)  →  NULL
```

А `TRUE AND UNKNOWN` — это `UNKNOWN`, и `WHERE` пропускает только `TRUE`. В итоге условие не может стать истинным **ни для одной строки**, и запрос возвращает пустой результат — молча, без ошибки. Это худший вид бага: не падает, а тихо отдаёт ноль строк.

`NOT EXISTS` этого лишён, потому что он не сравнивает значение со всем множеством, а проверяет сам факт существования строки. Подзапрос либо вернул строку, либо нет — третьего состояния здесь не бывает, `NULL` внутри него ни на что не влияет.

Практическое правило: `NOT IN` с подзапросом безопасен только тогда, когда столбец подзапроса объявлен `NOT NULL`. Во всех остальных случаях — `NOT EXISTS`.

## Q4. Места на борту и дубликаты

### 1. Защита от дублирования пассажиров

В демо-базе таблица называется `boarding_passes`, не `boardings`.

Для **одного билета** дублирование невозможно на уровне схемы — там три ограничения сразу:

```
PRIMARY KEY (ticket_no, flight_id)
UNIQUE      (flight_id, boarding_no)
UNIQUE      (flight_id, seat_no)
```

Остаётся теоретическая лазейка: пассажир с двумя разными билетами на один рейс получит два талона. В данных таких случаев ноль.

`DISTINCT` против `GROUP BY` на запросе «уникальные пассажиры рейса 543» (381 талон):

```
DISTINCT:   Unique (actual rows=381)  ->  Sort  ->  Nested Loop  ->  Bitmap Index Scan
GROUP BY:   Group  (actual rows=381)  ->  Sort  ->  Nested Loop  ->  Bitmap Index Scan
```

Планы совпадают с точностью до имени верхнего узла: `Unique` и `Group` — это одна и та же операция «схлопнуть соседние одинаковые строки после сортировки». Разницы в производительности нет, выбор чисто стилистический.

### 2. Посадочный талон без проданного билета

**Такая аномалия в этой схеме невозможна**, и это проверяется, а не предполагается. На `boarding_passes` висит составной внешний ключ:

```
FOREIGN KEY (ticket_no, flight_id) REFERENCES ticket_flights (ticket_no, flight_id)
```

Вставить талон на рейс, на который билет не продан, база просто не даст. Проверка `NOT EXISTS` по всем 1 894 295 талонам возвращает 0.

Если бы этого внешнего ключа не было, поведение зависело бы от того, что с чем соединять. Соединение `tickets` с `boarding_passes` напрямую такого пассажира сохранит — талон есть, строка найдётся. А вот `INNER JOIN` с `ticket_flights` его молча выбросит, потому что соответствующей строки там нет. Именно поэтому списки «кто летит» и «кто купил билет» на практике расходятся, и сверять их надо явно.

## Q5. DDL и блокировки на живой таблице

### 1. `ALTER TABLE ADD COLUMN` при открытой транзакции с `SELECT`

**DDL встанет в очередь и будет ждать, сколько потребуется.**

`ALTER TABLE` запрашивает `AccessExclusiveLock` — самый сильный уровень, несовместимый вообще ни с чем, включая обычное чтение. Открытый `SELECT` в незавершённой транзакции держит `AccessShareLock` — самый слабый, но и этого достаточно.

Воспроизведено на двух сеансах. Пока аналитик спит в транзакции, картина такая:

```
mode                 | granted
---------------------+---------
AccessShareLock      | t        ← держит аналитик
AccessExclusiveLock  | f        ← ALTER TABLE стоит в очереди
```

`pg_blocking_pids` показывает цепочку явно:

```
ждёт_pid | ждёт_запрос                    | блокирует_pid | блокирует_запрос
---------+--------------------------------+---------------+---------------------
    1937 | ALTER TABLE bookings.flights.. |          1930 | SELECT pg_sleep(25);
```

С `lock_timeout = '5s'` попытка завершилась ошибкой `canceling statement due to lock timeout`. Без таймаута она ждала бы бесконечно.

Самое неприятное здесь даже не это. Пока `ALTER TABLE` стоит в очереди на `AccessExclusiveLock`, **за ним выстраиваются все новые запросы к таблице, включая обычные `SELECT`** — PostgreSQL не пропускает их вперёд ожидающей сильной блокировки. Один забытый `BEGIN` плюс одна DDL-команда кладут таблицу целиком. Отсюда правило: перед любым DDL на нагруженной таблице сначала выставить `lock_timeout`, а потом проверить `pg_stat_activity` на предмет `idle in transaction`.

### 2. Почему `ADD COLUMN ... DEFAULT` мгновенен в PostgreSQL 11+

Проверено на `ticket_flights` — 2 360 335 строк, 154 МБ:

```
ALTER TABLE ticket_flights ADD COLUMN is_delayed boolean DEFAULT false;
Time: 3.016 ms
```

Три миллисекунды на 2,3 миллиона строк. Размер таблицы после операции — те же 154 МБ, ни одна страница не переписана.

До версии 11 такая команда переписывала всю таблицу: значение по умолчанию физически проставлялось в каждую строку. Начиная с 11-й PostgreSQL хранит его **в системном каталоге**, в `pg_attribute`:

```
attname    | atthasmissing | attmissingval
-----------+---------------+---------------
is_delayed | t             | {f}
```

`atthasmissing = true` означает «у строк, записанных до добавления колонки, значения на диске нет». При чтении такой строки движок видит, что в кортеже меньше атрибутов, чем в текущем описании таблицы, и подставляет `attmissingval`. Данные на диске не трогаются вообще.

**Что произойдёт при смене `DEFAULT` на `true`.** Проверено:

```sql
ALTER TABLE ticket_flights ALTER COLUMN is_delayed SET DEFAULT true;
```

`attmissingval` остался `{f}` — и это ключевой момент. Старые строки продолжают читаться как `false`, потому что `attmissingval` зафиксировал состояние на момент добавления колонки и больше не меняется. А новые вставки берут уже новый `DEFAULT`:

```
is_delayed | count
-----------+---------
f          | 2360335   ← старые
t          |       1   ← вставленная после смены DEFAULT
```

Параллельные `INSERT` при этом ведут себя предсказуемо: сама команда `ALTER ... SET DEFAULT` меняет только каталог и держит `AccessExclusiveLock` доли миллисекунды, после чего все новые вставки без явного значения получают `true`. Никакого «смешанного» состояния не возникает — граница проходит ровно по моменту фиксации `ALTER`.

### 3. Почему `CREATE INDEX` подвешивает запись и что делать

Обычный `CREATE INDEX` берёт на таблице `ShareLock`:

```
mode      | granted
----------+---------
ShareLock | t
```

`ShareLock` совместим с `AccessShareLock` (чтение) и несовместим с `RowExclusiveLock`, который нужен для `INSERT`, `UPDATE` и `DELETE`. Проверено прямо во время построения индекса:

```
SELECT count(*) FROM ticket_flights;   →  2360335    (прошёл)
UPDATE ticket_flights SET ...          →  заблокирован, lock timeout
```

Причина простая: индекс строится одним проходом по снимку данных, и если в это время кто-то меняет строки, индекс получится неполным.

**Решение — `CREATE INDEX CONCURRENTLY`.** Он берёт `ShareUpdateExclusiveLock`:

```
mode                      | granted
--------------------------+---------
ShareUpdateExclusiveLock  | t
```

Эта блокировка не конфликтует с `RowExclusiveLock`, и запись идёт свободно — проверено тем же `UPDATE`, который на этот раз прошёл.

**В чём компромисс.** Четыре причины, по которым так делают не всегда:

1. Таблица сканируется **дважды**: первый проход строит индекс, второй добирает строки, изменённые за время первого. Плюс между проходами команда ждёт завершения всех транзакций, начатых до неё, — одна долгая транзакция растягивает построение на своё время.
2. Нельзя запускать внутри транзакционного блока. Значит, нельзя обернуть миграцию целиком в `BEGIN ... COMMIT` и откатить при сбое.
3. При неудаче остаётся **нерабочий индекс** в состоянии `INVALID`. Он занимает место, обновляется при записи, но планировщиком не используется. Его нужно найти (`pg_index.indisvalid = false`) и удалить вручную, иначе он так и будет висеть мёртвым грузом.
4. Требуется больше ресурсов: два прохода плюс место под оба состояния.

Отдельно отмечу честный результат замера: на этой базе обычное построение заняло 2.52 с, а `CONCURRENTLY` — 2.25 с, то есть ожидаемого замедления не вышло. Это объясняется условиями: таблица на 1,9 млн строк целиком помещается в кеш, и параллельной нагрузки на запись не было вовсе. Разница в пользу обычного `CREATE INDEX` проявляется именно под конкурентной записью, которую в этом опыте воспроизвести не получилось.

## Q6. Агрегация и NULL в вычислениях

### 1. `AVG` при `NULL` в `actual_departure`

**`AVG` исключает такие строки полностью** — и из суммы, и из знаменателя. Это не то же самое, что считать их нулями.

Цифры по базе:

```
строк всего:                65 664
попало в расчёт AVG:        49 316
AVG (NULL пропущены):       00:12:21.88
AVG (NULL заменены на 0):   00:09:17.18
```

Расхождение — больше трёх минут, то есть около четверти величины. Знаменатель отличается на 16 348 строк, и это не шум, а целая категория рейсов:

| Статус | Рейсов | С фактическим вылетом |
|---|---|---|
| `Arrived` | 49 235 | 49 235 |
| `Scheduled` | 15 383 | 0 |
| `On Time` | 518 | 0 |
| `Cancelled` | 429 | 23 |
| `Departed` | 58 | 58 |
| `Delayed` | 41 | 0 |

Что из этого правильно — зависит от вопроса. «Средняя задержка **вылетевших** рейсов» — это `AVG` как есть, 12:21, и здесь пропуск `NULL` корректен: у ещё не вылетевшего рейса задержки просто не существует, нулём она не является. А вот «средняя задержка по расписанию за период» с подстановкой нулей была бы прямым искажением: будущие рейсы разбавили бы выборку и занизили результат.

Опасность в том, что `AVG` молча меняет знаменатель, и в отчёте этого не видно. Поэтому рядом со средним стоит выводить `count(actual_departure)` — тогда понятно, по скольким строкам оно посчитано.

### 2. `COUNT(aircraft_code)` против `COUNT(*)`

На этой таблице результаты **одинаковы**:

```
COUNT(*)                 65 664
COUNT(aircraft_code)     65 664
COUNT(actual_departure)  49 316
COUNT(actual_arrival)    49 258
```

Причина ровно одна и видна в схеме: `aircraft_code` объявлен `character(3) NOT NULL`. `COUNT(столбец)` пропускает `NULL`, но пропускать здесь нечего, поэтому он вырождается в `COUNT(*)`.

Разойтись они могут только на столбце, допускающем `NULL`, — и тут же рядом есть пример: `actual_departure` и `actual_arrival`, где разница составляет 16 348 и 16 406 строк соответственно.

Связь с ограничением прямая: **`NOT NULL` на уровне схемы — это гарантия, что `COUNT(столбец)` и `COUNT(*)` никогда не разойдутся.** Если такой гарантии нет, два похожих запроса дадут разные числа, и расхождение в отчёте будет выглядеть как ошибка, хотя оба запроса формально верны.

Практически же `COUNT(*)` предпочтительнее: он не требует разыменовывать конкретный атрибут и позволяет планировщику выбрать `Index Only Scan` по любому подходящему индексу. `COUNT(столбец)` стоит писать осознанно — именно тогда, когда нужно посчитать строки с заполненным значением.
